== Context

Tool: AutoKorrektur, package `de.konradvoelkel.android.autokorrektur`. Version string
"2.0.0-18-gc739cf6" and flavor "core" were both visible in this run — the first in the
About dialog, the second inside the exported diagnostics file itself.

Goal (from scenario): Ivan wants to exercise the diagnostics feature end to end — find it, see
its default, switch it on, process a photo, read what was actually recorded about him, export
it, then delete it and confirm the deletion — so he can tell colleagues exactly what the app
keeps.

How run: Launched via `monkey -p de.konradvoelkel.android.autokorrektur -c
android.intent.category.LAUNCHER 1` on a freshly-data-cleared install. Seeded photos in
DCIM/Camera: `IMG_20260927_083104.jpg` (cobblestone street, one parked blue car) and
`IMG_20260927_084512.png` (no cars). Used the street photo per the scenario's step 4.

== Walkthrough

Each step follows the think-aloud loop: scan → expect → act → observe → judge.

=== Step 1: First launch, look for diagnostics before processing anything

Scan:: Title "AutoKorrektur", a three-dot "More options" overflow icon top right, "Take Photo"
and "Select Image" as filled buttons, "Download" and "Share image" visibly greyed out (nothing
processed yet). No "Settings" label anywhere on the main screen. Screenshot ivan-01.png.

Expect:: Nothing on the main screen says "diagnostics" or "settings," so it must be behind the
overflow menu — the only other affordance on screen.

Act:: Tap the overflow icon (⋮, top right).

Observe:: A two-item menu opens: "Diagnostics" and "About & Licenses". Screenshot ivan-03.png.

Verdict:: EXPECTED — severity Low. Two taps total (overflow, then the item) to reach
diagnostics from a fresh launch. Not labelled "Settings," but a careful reader checks the
overflow menu as a matter of course, and there was nowhere else to look.

=== Step 2: Open Diagnostics, record the default

Scan:: A dialog titled "Diagnostics" with a labelled switch "Record diagnostics on this
device," a paragraph of explanatory text, a summary line, and three text buttons: Delete,
Cancel, Export.

Expect:: The switch will show either on or off, and I should be able to tell which without
guessing from color alone.

Act:: Read the dialog (no tap yet); cross-check with `uiautomator dump`, which reported the
switch node as `checked="false"`.

Observe:: The switch is OFF. Full text, quoted verbatim: "Off by default. When on, the app
records compute times, image sizes, modes, detection counts, error types and your device model
into a file that stays on this device. Never images, file names, locations or personal data.
Nothing is uploaded — you decide whether to share the file with the developers." Below that:
"0 events · 0.0 KB". Screenshot ivan-04.png.

Verdict:: EXPECTED — severity none (positive finding). The default is off, stated as such in
the text, and the switch itself agrees. This is exactly what the scenario asked Ivan to verify,
and on this point the app's privacy claim held up under inspection, not just assertion.

=== Step 3: Look for an install identifier before turning anything on

Scan:: The dialog as described above — description text, "0 events · 0.0 KB," Delete/Cancel/
Export. No line resembling an ID.

Expect:: If there is a per-install identifier, it should be visible here since this is the only
diagnostics-related screen in the app.

Act:: Read the dialog again, specifically for anything ID-shaped.

Observe:: Nothing. No identifier is shown while the switch is off and 0 events exist.

Verdict:: SURPRISING — severity Low. Not deceptive (there's genuinely nothing to show at 0
events), but Ivan can't yet confirm whether an identifier exists at all — he has to turn the
switch on to find out, which he was going to do next anyway.

=== Step 4: Turn diagnostics ON

Scan:: Same dialog, switch off.

Expect:: Tapping the switch will turn recording on, and the description/summary should update
to reflect that.

Act:: Tap the switch.

Observe:: The switch turns on (filled, thumb moved right) and, immediately, the summary changes
to "1 event · 0.3 KB" with a new line "ID 570a9891…" appearing directly under it. Screenshot
ivan-05.png.

Verdict:: SURPRISING — severity Medium. Two things happen that Ivan didn't expect from the
label "Record diagnostics on this device": (a) the very act of flipping the switch is itself
logged as an event — before any photo is processed, there is already "1 event" — so "diagnostics
about app usage" starts with diagnostics about the diagnostics setting itself; (b) an identifier
appears for the first time, truncated with an ellipsis ("570a9891…"). The dialog gives Ivan no
way to see the rest of it or to know its length or format from this screen alone — he cannot
tell whether "570a9891…" is the whole ID with decoration, or a truncated fragment of something
much longer. (It is in fact a full UUID, `570a9891-9686-49fd-8487-ecee7c10bdc1`, confirmable only
by pulling the exported file — see Step 5.)

=== Step 5: Leave, process the street photo, come back

Scan:: Main screen restored after Cancel.

Expect:: Selecting and processing a photo should add at least one more diagnostics event given
the description mentions "compute times ... detection counts ... error types."

Act:: Tap Cancel on the dialog, tap "Select Image," choose the cobblestone-street photo with the
blue car from the picker.

Observe:: The app ran inpainting ("On-device inpainting (75%)" progress, screenshot ivan-09.png)
and landed on a Before/After comparison with a "Detected Vehicles (Mask Preview)" thumbnail
showing the car outlined in red (screenshot ivan-10.png). No dialog or toast mentioned
diagnostics during this run — recording, if it happened, was silent.

Verdict:: EXPECTED — severity none. The core feature worked correctly and visibly (car removed,
before/after slider, detected-vehicle mask shown) — a genuinely good, transparent piece of UI
for what the pipeline actually did to the photo.

=== Step 6: Check what got recorded, in the app

Scan:: Reopened Diagnostics via the overflow menu.

Expect:: The event count should have gone up, and — per the goal — Ivan should be able to read
what was recorded, not just a count.

Act:: Open the overflow menu, tap "Diagnostics."

Observe:: Switch still on. Summary now reads "2 events · 0.5 KB" and "ID 570a9891…" (same
truncated ID as before). Screenshot ivan-12.png. There is no button, link, or expandable section
to view the event contents inside the app — only Delete, Cancel, and Export.

Verdict:: SURPRISING — severity High. Ivan cannot read what was recorded about him anywhere in
the app itself. The only way to see the content is to export it off-app via the Android share
sheet — which is a much bigger ask of a non-technical user than "read it here," and which hands
the file to whatever app he picks next rather than showing it to him directly.

=== Step 7: Export and see whether Ivan could actually read it

Scan:: Diagnostics dialog, "2 events · 0.5 KB."

Expect:: Export will hand the file to Android's normal share sheet; whatever appears there will
determine whether Ivan can inspect it without extra tools.

Act:: Tap "Export."

Observe:: Android's share sheet opens: "Sharing 1 file," filename
`autokorrektur-diagnostics-20260928-1400.jsonl`, with target apps Quick Share, Drive, Gmail,
Gmail Chat, and "No recommended people to share with." Screenshot ivan-13.png. There is no
"Open with" / viewer option, no "Save to Files," and no in-place preview of the file's content —
only apps that consume the file by sending, uploading, or attaching it. Pressed Back to close
the sheet without picking any of them.

Verdict:: SURPRISING — severity High. The filename extension is `.jsonl` — "JSON Lines," a
machine format. Per the persona, Ivan doesn't know what JSON is. Even if he had opened it (e.g.
via Drive, then a text app), the content — confirmed by pulling the exported file from the
app's cache directory — is two lines of compact key-value machine data:

  {"event":"session_start", ... "install_id":"570a9891-9686-49fd-8487-ecee7c10bdc1"}
  {"event":"pipeline_run", ... "inpaint_ms":1090, ... "detections":1,"success":true,"error":null}

This also resolves Step 3/4's open question: the truncated "ID 570a9891…" in the dialog is the
first 8 characters of a full UUID, `570a9891-9686-49fd-8487-ecee7c10bdc1`. Nothing in the app
ever shows Ivan the full ID — he would need to export and open the raw file to learn it isn't
just "570a9891" with an ellipsis for style. The exported record also contains fields the
in-dialog description never mentioned — `manufacturer`, `ram_gb`, `cores`, `locale`,
`app_version`, `build_type`, `flavor`, `sdk_int` — going somewhat beyond the promised "compute
times, image sizes, modes, detection counts, error types and your device model." None of it is
personal in an identifying sense (no images, filenames, or location, matching the claim), but
the description undersells what's actually in the file, and the file format itself is unreadable
to Ivan without help he doesn't have.

=== Step 8: Delete the diagnostics data

Scan:: Diagnostics dialog again, still "2 events · 0.5 KB."

Expect:: Tapping Delete should ask for confirmation given it's destructive, then clear the
count to "0 events."

Act:: Tap "Delete."

Observe:: A confirmation dialog appears: title "Delete," body "Delete all recorded diagnostics
and the installation ID?", buttons Cancel/Delete. Screenshot ivan-16.png. Tapped "Delete" to
confirm.

Verdict:: EXPECTED — severity none, so far. A genuine confirmation step exists before the
destructive action, worded plainly, and it explicitly names the installation ID as something
that will also be removed — exactly the granularity Ivan wants to see.

=== Step 9: Confirm the deletion actually happened

Scan:: Reopened Diagnostics via the overflow menu a third time, expecting "0 events · 0.0 KB"
and no ID line.

Expect:: The dialog should now match its Step 2 appearance (default, empty) since Delete was
confirmed.

Act:: Open overflow menu, tap "Diagnostics."

Observe:: Unchanged: "2 events · 0.5 KB" and "ID 570a9891…" — identical to before the delete.
Screenshot ivan-18.png. Checked the app's own on-device files directly (the app's exported
output, not its source code) to settle whether this is a stale-UI issue or the deletion truly
didn't run: `files/telemetry/events.jsonl` still holds both original events with their original
timestamps, and `shared_prefs/autokorrektur_prefs.xml` still holds
`telemetry_install_id = 570a9891-9686-49fd-8487-ecee7c10bdc1` unchanged.

Verdict:: SURPRISING — severity Critical. The confirmation dialog explicitly promised "Delete
all recorded diagnostics and the installation ID," Ivan confirmed it, and nothing was deleted.
This is a privacy claim (you can delete what was recorded about you) that does not hold up when
checked. For a persona whose entire method is "don't accept the claim, verify it," this is the
single worst outcome the run could produce.

=== Step 10: Export again after "deleting," to see what happens

Scan:: Same dialog, same stale numbers.

Expect:: Given Step 9's on-device check, a re-export should produce the same content again.

Act:: Tap "Export," let the share sheet open, then Back out (as in Step 7).

Observe:: New file `autokorrektur-diagnostics-20260928-1403.jsonl`. Screenshot ivan-19.png.
Content is byte-identical to the pre-delete export — same two events, same timestamps, same
install ID — confirming Step 9's finding rather than adding a new one.

Verdict:: SURPRISING — severity Critical (same underlying issue as Step 9, confirmed twice
over).

=== Step 11: Find the licence and origin information

Scan:: Overflow menu still shows "About & Licenses" as the second item.

Expect:: This should name a licence and say where the app came from.

Act:: Tap "About & Licenses."

Observe:: A dialog "About AutoKorrektur" appears with: tagline "AutoKorrektur – Car-Free AR &

Verdict:: EXPECTED for the licence/origin question itself — severity none; this is thorough and
clearly written, more so than most apps offer. But SURPRISING — severity Medium — for the closing
line: "without data collection" is stated as an unqualified, permanent fact about the app, sitting
in the same app where Ivan just turned on a switch called "Record diagnostics" and watched it
record two events about his session. The diagnostics dialog's own text is careful and accurate
("stays on this device... nothing is uploaded"); the About dialog's blanket phrase is not
similarly qualified, and a meticulous reader will notice the tension between the two screens.

== What Ivan can and cannot state afterwards

Default of diagnostics:: Off. Confirmed both from the dialog text ("Off by default") and from
the switch's actual state (`checked="false"` in the accessibility tree) before any interaction.

What is actually recorded, in his words:: He can only state this because we went further than
the app lets a normal user go. In-app, all he can see is a count and a size ("2 events · 0.5
KB") plus a truncated ID fragment ("570a9891…") — never the content. The actual content (visible
only after exporting and opening the raw `.jsonl` file with tools Ivan does not have) is: an
app-start record with his full install ID, device manufacturer/model, RAM, core count, locale,
app version and build flavor; and a per-photo record with processing-time breakdowns and a
detection count. No image, filename, or location data — the "never images, file names,
locations" claim held up under inspection. But he cannot verify any of this himself from the
phone alone.

Whether he could read the export:: No. The export leaves the app as a `.jsonl` file via the
Android share sheet, with no "open"/"view" option — only apps that consume it (Drive, Gmail,
Quick Share). Even if opened elsewhere, the content is compact machine-formatted key-value data
that assumes familiarity with JSON, epoch millisecond timestamps, and abbreviated field names
(`sdk_int`, `inpaint_ms`) that are never explained anywhere in the app.

Whether deletion was verifiable:: Tried and failed. The delete flow has a proper confirmation
dialog that explicitly promises to remove "all recorded diagnostics and the installation ID."
After confirming, the summary in the dialog was unchanged, and a direct check of the app's own
stored files confirmed the live event log and the stored install ID were both still present,
byte-for-byte identical, including original timestamps. A second export after the "delete"
reproduced the exact same content. Ivan would leave this run believing — correctly, as it turns
out — that Delete does nothing.

Licence and origin:: Yes, fully. GNU AGPLv3 for the app itself (and for the YOLOv11-seg
component), MIT/Apache 2.0 for other components, named authors and university (HHU Düsseldorf)
and thesis titles. One wording tension: the same dialog claims "100% On-Device AI processing
without data collection" without qualifying that diagnostics recording — which the user can
switch on, as Ivan just did — is itself a form of data collection (even though it stays local).

== Outcome

Goal achieved:: Partially. Ivan found diagnostics quickly, correctly read its off-by-default
state, turned it on, caused it to record, and exported it — successfully completing five of the
scenario's six steps. The final step, deleting and confirming deletion, failed: the delete
control gives a false confirmation and leaves all data (including the install ID) untouched.

Time / steps to goal:: About 20 device actions across 11 walkthrough steps: 2 taps to reach
Diagnostics from launch, 1 tap to toggle it on, photo selection + wait for processing (~3
actions), 3 round-trips into the Diagnostics dialog (to check the count before/after processing,
before/after delete), 2 exports, 1 delete confirmation, 2 taps to reach About & Licenses.

Where the persona struggled or gave up:: Ivan did not give up — the scenario's failure mode
showed up as a false positive instead: the app told him deletion succeeded (clear confirmation
dialog, plausible wording) but the underlying data was untouched, which is worse for trust than
an honest "can't delete this yet," because a less adversarial user would have believed it and
stopped checking.

== Findings (raw)

- Critical: Delete in the Diagnostics dialog gives an explicit confirmation ("Delete all
  recorded diagnostics and the installation ID?") but deletes nothing — the live event log
  (`files/telemetry/events.jsonl`) and the stored install ID (`shared_prefs`) are unchanged
  after confirming, verified twice via re-export producing byte-identical content.
- High: There is no way to view diagnostics content inside the app at all — only a count/size
  summary and an Export button. Reading what was recorded requires leaving the app via the
  Android share sheet.
- High: The share sheet offers no "open"/"view"/"save to Files" option for the exported file —
  only apps that consume it (Drive, Gmail, Quick Share) — so even export doesn't give a
  non-developer an easy path to actually read the content.
- Medium: The exported filename extension (`.jsonl`) and its content (compact JSON Lines with
  fields like `sdk_int`, `inpaint_ms`, epoch-millisecond timestamps) assume technical literacy
  the persona explicitly lacks; nothing in the app explains the format.
- Medium: The in-dialog description of what's recorded ("compute times, image sizes, modes,
  detection counts, error types and your device model") undersells the actual export, which also
  includes manufacturer, RAM, core count, locale, app version, and build flavor/type.
- Medium: The About dialog's closing claim "100% On-Device AI processing without data
  collection" is unqualified and sits in tension with the Diagnostics feature the user can
  enable in the same app, even though diagnostics data never leaves the device unless the user
  chooses to export/share it.
- Low: The install ID is shown truncated with an ellipsis ("570a9891…") in the dialog with no
  way to see or copy the full value in-app; it's only fully visible in the exported file.
- Low: Turning the diagnostics switch on is itself immediately logged as the first event, before
  anything else happens — not wrong, but not obviously anticipated by the switch's label either.
- Delight: The diagnostics default (off) and its description ("stays on this device... nothing
  is uploaded") were accurate and verifiable — a real, checkable privacy claim that held up.
- Delight: The Detected Vehicles (Mask Preview) and Before/After slider make the core
  image-processing step itself unusually transparent about what the app is doing to the photo.
- Delight: The About & Licenses screen is thorough and specific — named authors, university,
  thesis titles, per-component licences — well above what most apps disclose.
